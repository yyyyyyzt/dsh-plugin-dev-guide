## 0. 一句话定位

> 面向电力互联网产品技术方案预审这一「高频、模板化、强规则但又需要专家判断」的工程场景，提出一种**按可验证性分配权限**的人机协同审查方法：确定性校验器拥有登记问题的权力，LLM 只能在校验器划定的候选证据范围内提出建议并被逐字引文门禁约束，专家在对话中确认/驳回/改写，最终结论由确定性策略而非模型给出；专家反馈在规则层（而非模型层）闭环，形成可审计的学习。

关键词候选：technical solution review; neuro-symbolic compliance checking; evidence-grounded LLM; human-in-the-loop; rule-level feedback learning; LLM agent plugin。

## 2. 贡献（C1–C5）

### C1 按可验证性分级的规则权限模型（hard / hybrid / soft）

- 内容：规则的权限由「能否被程序确定性验证」决定。`hard` 只由校验器判定（LLM 登记被拒：`HARD_RULE_VERIFIER_OWNED`）；`hybrid` 由校验器划定候选片段，LLM 只能在候选范围内判断；`soft` LLM 可提但一律 `pending`，永不计入结论。
- 为什么新：现有神经-符号合规审查（如 PolicyGuard，arXiv 2606.32004）把「符号规则 + LLM 做原子抽取」拆开，但权限是对称的——LLM 的抽取结果直接进入符号求值。我们的差异是**不对称授权**：LLM 的输出在到达结论之前必须穿过校验器划定的空间边界（候选 range）和门禁，并且规则的 tier 本身是一个可被专家反馈调节的参数（`soft → hybrid` 升级提示）。
- 证据：消融 S−verifier（hybrid 不给候选）vs S-full 的 P/R；门禁原因分布中 `OUT_OF_CANDIDATES` 的占比（说明候选边界实际拦下了多少越界判断）。

### C2 逐字引文门禁 + 候选区间约束 + 缺失证据（absence evidence）

- 内容：LLM 登记问题必须附 8–300 字可在原文中归一化命中的引文（`QUOTE_NOT_FOUND` 等 7 种拒绝原因），hybrid 规则的引文还必须与候选区间相交；校验器可产生零长度的「缺失」证据（如「缺失：实施方案」「未提及：loadtest」），把「没写」也变成可定位、可展示的证据。
- 为什么新：逐字引文校验（VeriQuote、OpenAI cookbook 的 zero-token gate、HalluHard）解决的是「引文是否真的在源里」。我们在其上加了两件事：(a) 引文必须落在**由规则校验器定义的语义相关区域**内，而不仅是「在文中某处」；(b) 缺失型问题（审查中最常见的一类意见——「建议补充 X」）有了形式化证据载体。审稿人可能说 (a) 是工程细节，所以要用数据证明它独立贡献精确率（S−gate vs S-full，以及门禁原因分布）。
- 证据：证据有效率、S−gate 消融、门禁重试一次后的恢复率（T-PRO-09 路径）。

### C3 建议-确认-策略三段式治理：AI 永不出结论

- 内容：`ai_verdict` 是建议，`final_verdict` 只能由专家通过 `review_decide(set_final_verdict)` 写入；结论策略是对**专家确认后问题集合**的确定性函数（blocker → 不通过；major 或 minor ≥ 阈值 → 建议整改）。因此「模型与专家的差异」被拆成两个可分别度量的量：问题集合的差异（采纳/驳回/改写）与策略的差异（`verdictDelta`）。
- 为什么新：多数 LLM 审查工作（代码审查的 CodeRabbit / BitsAI-CR / RovoDev，文档审查的 Gulave 2025）把人类反馈当作评测标签或过滤器训练信号，结论仍由模型或人单方面给出。我们把结论的「生成权」从模型手里完全拿走，使系统在组织治理上可被接受（AI 预审不替代专家签字），并让 H3 成为可检验的问题：策略结论比模型直接结论更接近专家吗？
- 证据：B1 / S−policy vs S-full 的 kappa、宏 F1、3×3 混淆矩阵；在线集 `aiVerdictAtFinalize` vs `final_verdict` 的 kappa 与 `verdictDelta` 分布。
- 风险：如果专家几乎总接受推荐结论（kappa 很高），审稿人可能质疑「专家只是橡皮图章」；需要同时报告专家对**问题集合**的改动率，证明确认环节有实质内容。

### C4 规则层（而非模型层）的在线反馈学习，带生命周期与审计

- 内容：对话中的采纳 = TP、改写 = TP（措辞范例）、驳回 = FP、专家新增 = FN；回流到 `rule_overrides.stats`、`exemplars`（措辞范例，上限 N）与 `rule_candidates`（新规则草案 LRN-xxx）。规则按 候选 → 草案 → 生效 → 停用 生命周期演进，每次改动留审计。常被驳回的规则在召回时自带告警（`warn`），由 agent 提示专家调参，不自动改。
- 为什么新：代码审查领域已证明「反馈是可学的」（CodeRabbit 实证：56.3% 评论被拒，轻量模型预测拒绝 F1 76%；BitsAI-CR 用 outdated rate 剪枝规则，精确率 60% → 75%）。但这些都是离线、以模型/过滤器为学习载体。我们的学习载体是**人类可读的规则参数与措辞范例**，在对话内即时生效，无需微调，且每一步可被看板审计——适合专家数量少、数据不出域的组织场景。
- 证据：采纳率滑动曲线（窗 5）的斜率与 95% CI；规则级精确率随审查序号的收敛；S−memory 消融（近似）；`rule_candidates` 转化为生效规则的数量（定性案例）。
- 风险：在线集样本量可能只有几十份，学习曲线的统计显著性弱。应对：把 H2 定位为「可观测趋势 + 案例」而非强统计结论，并在合成集上做「模拟专家」的敏感性实验（用真值标签模拟 adopt/reject，看 warn 机制能否在 k 次内识别出被故意调坏的规则）。

### C5（工程贡献）作为 agent 宿主插件而非独立系统的实现

- 内容：整个方法以 DSH 插件形式交付：9 个工具、1 个 skill、1 个 persona、存储域、只读路由与看板 tab；复用宿主的对话、`ask_user_question`、文件系统、`present`、设置与 Word→Markdown 技能。代码只做审查本身（符合「其他能力装插件解决」的约束）。
- 为什么值得写：*Applied Sciences* 类期刊看重「可复用的工程形态」。可以给出：实现规模（LOC、工具数）、每次审查的工具调用次数与耗时（`reviews.metrics`）、宿主约束如何塑造设计（命令不经模型 → 命令只能做查询；无二级索引 → 内存筛选；`domain` 版本不匹配 → 迁移脚本）。
- 证据：`metrics.toolCalls / gateRejects / 耗时`；bench（200 KB ≤ 2 s）；与旧版 Python 原型的功能/规模对照表。
