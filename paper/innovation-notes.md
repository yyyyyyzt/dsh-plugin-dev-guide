## 0. 为什么不能讲「准确率」的故事

1. **会被下一代模型淹没。** 任何「我们的流水线比直接问模型高 x 个点」的结论，半年后换个模型就失效；审稿人也知道这一点。
2. **错位于时代问题。** 当前的研究前沿是模型自我改进（自我生成训练数据、自我评估、自我修改工具链）。在这个背景下，一个组织级应用系统的真问题不是「AI 审得准不准」，而是**「AI 系统里的领域知识从哪来、以什么形态存在、谁有权改它、它怎么随使用而生长、生长时怎么不失控」**。这是知识工程 + 治理的问题，不是指标问题。
3. **我们的场景恰好是这个问题的干净样本。** 技术方案预审：知识高度专家化、文档高度模板化、后果高风险（结论要签字）、专家少而审查多、知识在变（新接入模式、新风控要求）。这几个特征叠加，使「知识怎么进系统」比「模型多强」更决定成败。

因此论文的主张要从「方法 X 提高了 F1」改为「我们**定义**了一个在 LLM 时代普遍存在但未被命名的问题，**提出**一种组织该问题的框架，并用一个真实部署的系统**展示**该框架下的解法与代价」。F1 只是其中一张表。

## 1. 问题定义：审查知识的引入问题（Review-Knowledge Ingestion Problem）

### 1.1 现象

把专家审查知识送进一个基于 LLM 的审查系统，当前实践只有三条路，每条都在特定方式上「失真」：

| 引入方式 | 知识的存在形态 | 失真模式 | 我们的旧版原型里的对应 |
|---|---|---|---|
| **关键词化**（规则 → 字符串匹配） | 几个子串 | 知识退化：「有压测两个字」= 「做了压测」；否定、占位、空节全看不出 | 旧版 24 条规则的 `rule` 检查，B0 基线复刻 |
| **提示词化**（规则 → prompt 清单） | 自然语言段落 | 知识不可验证、不可审计：模型「看过」规则，但它的判断无法回溯到规则，也无法回溯到原文；错了不知道错在哪条 | 旧版 `llm` 检查路径，B1 基线 |
| **片段化**（历史意见 → RAG） | 向量片段 | 知识不积累：每次检索临时拼凑，100 次审查后系统和第 1 次一样「笨」；片段之间无矛盾标注、无关联 | 旧版未做但用户曾考虑；用户决策 1「不用向量库」 |

三者共享一个根因：**知识被当作「给模型看的输入」，而不是「系统拥有的、带权限与出处的资产」。**

### 1.2 两个张力（这是问题的「硬核」）

- **可验证性张力。** 审查知识的可验证性是一个谱：「实施方案一节是否存在」几乎完全可验证；「风险评估是否充分」几乎完全靠判断。越不可验证的知识越需要模型，越可验证的知识越不该交给模型（模型会在确定性问题上犯低级错误且无法解释）。现有三条路对所有知识一视同仁——要么全交给字符串，要么全交给模型。
- **生长张力。** 知识必须随使用生长（专家的每一次驳回都是信息），但在高风险场景里，生长不能由系统单方面完成（自我改进的规则改坏了，签字的还是专家）。现有做法要么不生长（prompt 写死），要么生长在人看不见的地方（微调、过滤器权重）。

### 1.3 正式表述（论文 §1 末尾给出）

> 给定一个领域审查知识集合 K（规则、范例、历史判断）和一个 LLM 审查系统 S，**审查知识引入问题**是：为 K 选择一种存在形态与权限分配，使得 (i) 每条知识的使用能回溯到它本身和被审文档的具体位置（可审计），(ii) 不同可验证性的知识获得与之匹配的决策权限（权限随可验证性），(iii) K 能从专家与 S 的交互中增量更新（可生长），且 (iv) 更新受人类权限约束且可回滚（有界生长）。

这四条就是后面所有设计决策与评测维度的来源。

## 2. 叙事：从「检索/提示」到「编译」——审查知识的编译器

借 Karpathy 的 LLM Wiki 隐喻（RAG 是解释器，Wiki 是编译器：把理解成本从查询时刻前移到摄入时刻，产物持续生长、可追溯）。我们的系统是这个隐喻在**审查知识**上的具体化，但有三点关键不同，正是论文的概念贡献所在：

| 维度 | LLM Wiki | 本文：审查知识编译器 |
|---|---|---|
| 源（raw） | 文档 | 历史意见、模板、被审方案、**专家在复核对话中的决定** |
| 编译器 | LLM 单独 | **专家 + LLM 的对话协议**（复核即编译：采纳/驳回/改写/新增各对应一种编译动作） |
| 编译产物（IR） | 给人读的 Markdown 页面 | **可执行、带类型的规则包**：每条规则携带 tier（类型）、校验器（可执行部分）、措辞范例、统计、来源 |
| 类型系统 | 无 | **tier = 知识的可验证性类型**，决定该知识的决策权限（hard 自动登记；hybrid 划候选给模型；soft 只能提醒） |
| Lint | 死链、孤页、矛盾 | 驳回率告警、规则候选、tier 升级提示 |
| 构建日志 | wiki-log | `audit[]` + `rule_candidates` + 规则包版本 |
| 自我改进边界 | 无 | **系统可改参数、措辞、新增 soft 规则；不能自行提升 tier**（权限提升必须由人完成） |

一句话定位（摘要用）：

> 我们把 LLM 审查系统中的领域知识从「给模型看的提示」重新定义为「系统持有的、按可验证性分型、可执行、可审计、经专家对话增量编译的资产」，并在能源互联网平台的技术方案预审中用一个 agent 插件实现与检验这一定义。

## 3. 贡献（概念 > 框架 > 系统 > 证据）

### C1（概念）审查知识的可验证性类型系统与「权限随可验证性」原则

- 把 hard / hybrid / soft 从「规则的一个字段」提升为**知识的类型**，并给出判型准则：能否由确定性过程在文档上给出带位置的证据（含「缺失」证据）。
- 原则：知识类型决定决策权限；模型的输出只能在比它权限更高的类型划定的空间内（候选 range）生效。这把「LLM-as-judge 可靠性」这个泛问题转化为「每条知识该不该让模型判」这个可操作的局部问题。
- 这是对 §1.2 可验证性张力的回答。

### C2（框架）对话即编译：专家复核协议作为知识编译器

- 四种专家动作 → 四种编译动作：采纳 = 固化范例；改写 = 更新措辞 IR；驳回 = 累积反例并触发 lint；新增 = 产生新知识候选（soft 类型入口）。
- 编译产物有明确的 IR 格式（规则 YAML schema）、分层（shipped / learned）、生命周期（candidate → draft → active → retired）与构建日志（audit）。
- 这是对 §1.2 生长张力的回答，并且是一个**有界自我改进**的实例：系统在类型边界内自我修改，边界本身只有人能动。可以在讨论里与 RSI 研究对话：在高风险组织场景中，自我改进不是「能不能」，而是「改进的类型边界划在哪」。

### C3（系统）在通用 agent 宿主中以插件形态实现该框架

- 不新建系统：所有通用能力（对话、提问、文件、交付、设置、Word 转换、模型访问）来自宿主；插件只实现知识编译器本身（规则包 + 校验器 + 门禁 + 协议 + 记忆 + 看板）。
- 论文价值：说明该框架的「最小实现面」有多大（工具数、LOC、表数），以及宿主约束如何塑造设计。作为 *Computers* 读者关心的「可复用性」证据。

### C4（证据）在真实试点（上百份审查）与合成集上检验四条性质

对应 §1.3 的 (i)–(iv)，各自一组指标，见 §5。精确率/召回率只服务于 (ii) 的一个子问题（权限分配是否比不分配更好），不再是主线。

### 方法层面明确声明为组合与微改

确定性校验器（结构检查的常规做法）+ 逐字引文门禁（VeriQuote 一类已有）+ 确定性结论策略（简单规则）+ 规则级统计记忆（代码审查系统已用）。论文不声称任何单个组件新颖；声称的是**把它们组织在一个类型系统与编译隐喻之下，并由此得到可审计、可生长的知识资产**。审稿人若问「哪里新」，答案在 C1、C2，不在组件。

## 4. 相关工作（按「知识如何进入系统」重新组织）

| 路线 | 代表 | 知识形态 | 对 §1.3 四性质的满足 |
|---|---|---|---|
| 提示词清单 / 多角色 agent | MARV（SRS 验证，2025）、Gulave & Moholkar 2025 | prompt | 不可审计、不分权限、不生长（或在模型层生长） |
| RAG over 历史审查 | 通用做法 | 向量片段 | 可部分追溯源，但不生长、不分权限 |
| 神经-符号合规 | PolicyGuard（arXiv 2606.32004） | 逻辑规则 + 原子抽取问题 | 可审计、部分权限分离（符号求值），**但无类型系统、无专家编译回路、无有界生长** —— 最近邻，必须正面对比 |
| 证据感知人机协同 | ReqPlan-Eval（*Computers* 2026） | 路由信号 + 可检视记录 | 强调可检视与选择性人审；不做知识资产化 |
| 引文忠实性 | VeriQuote、OpenAI zero-token gate、HalluHard | 逐字引文 | 解决「证据是否真在源里」，我们复用并加候选区间约束；属组件 |
| 反馈学习的 LLM 代码审查 | CodeRabbit 实证（56% 被拒、拒绝可学 F1 0.76）、BitsAI-CR（按 outdated rate 剪规则）、uReview、RovoDev | 过滤器 / 规则剪枝 | 证明「反馈有信息」；学习在模型/过滤器层，人看不见；对象是代码 |
| 知识编译 | Karpathy LLM Wiki（2026）及衍生实现 | 互链 Markdown | 提供编译隐喻；产物不可执行、无类型、编译器无人类权限边界 |
| 自我改进 agent / RSI | （综述级引用即可） | — | 提供「有界自我改进」的对话对象；我们不做模型层自我改进 |

补检索待办：电力/能源行业信息化方案评审实践（多为规章 + 会审）；中文模板化技术文档的结构化解析；知识工程中「可验证性/可操作性分级」的既有概念（如 requirements 的 verifiability 属性，ISO/IEC/IEEE 29148 有定义——可借用来给 C1 找学术根）。

## 5. 评测重设计：围绕四条性质，而非围绕 F1

| 性质 | 问题 | 数据 | 指标 / 分析 | 已有设计对应 |
|---|---|---|---|---|
| (i) 可审计 | 每条产出意见能否回溯到规则与原文位置？ | 在线集 | 证据有效率；门禁拒绝原因分布；意见 → 规则 → 证据 三级可回溯比例（应为 100%，报告例外） | evaluation §4.3；`gate.reasons` |
| (ii) 权限随可验证性 | 分型授权是否优于不分型？ | 合成集 + 在线集 | B0 / B1 / S−verifier / S−gate vs S-full 的 P/R/F1；**按 tier 分组的驳回率**（预期 hard < hybrid < soft，这是类型系统有效的直接证据）；hard 规则被专家驳回的案例分析 | H1、消融表 |
| (iii) 可生长 | 知识随使用增长了吗？ | 在线集时间序列（上百份） | 规则包版本演化曲线；每份审查产生的知识增量（新范例 / 调参 / 新候选 / 新生效规则）；采纳率滑动曲线；规则级精确率收敛；`soft → hybrid` 升级事件 | H2、§4.4 |
| (iv) 有界生长 | 生长是否受控、可回滚？ | 在线集 + 合成「模拟专家」 | 全部变更的 audit 覆盖率；人工 vs 系统发起变更的比例；故意调坏规则后 lint 告警所需审查次数；回滚案例 | 新增（模拟专家脚本，S5） |
| 结论权 | 策略结论 vs 模型结论 vs 专家 | 在线集 | kappa / 宏 F1 / `verdictDelta`；专家对问题集合的改动率（防「橡皮图章」质疑） | H3 |

### 8.1 S3a 实现中值得写进论文的三个事实（捎带记录，2026-10-19）

- **类型系统是静态检查而非口头约定**：`parseRulePack` 在加载时拒绝 soft 带校验器、hybrid/hard 无校验器、hard 树里出现非 decisive 的 `statement` 或 `whenNoCandidate: pending`、引用不存在的词表 key；任何一条失败整包不加载。论文 §3（C1）可直接引用这组不变量作为「权限随可验证性」的可执行定义，而不是只画一张三级表。
- **分级结果的真实分布**：旧 24 条按可验证性逐条分级后是 hard 6 / hybrid 13 / soft 5；加 4 条模板结构规则后为 10 / 13 / 5。hybrid 占近半——说明「关键词命中 ≠ 要求满足」是常态，这正是 C1 中「候选交 LLM、证据必须落在候选内」这一层存在的实证理由。写论文时用这个分布，不用早先误记的 11/12/5。
- **证据门禁需要的定位策略不止「找到引文」**：同一句话在同一章节重复出现（种子方案的「与现有数据架构保持一致」）时，门禁必须优先取落在候选片段内的命中，否则会把合法证据判为 OUT_OF_CANDIDATES。这是一个很小的实现细节，但它说明「证据落在候选内」是对位置而非对字符串的约束——论文里讲门禁时用一句话点出即可。
