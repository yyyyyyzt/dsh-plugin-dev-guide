## 摘要

大模型（LLM）越来越多地在前置环节替专家预筛技术文档，但专家的评审知识进入这类系统的方式，通常是关键词规则、提示词清单，或在历史评审记录上做检索；这三条路线各丢掉一个高利害评审必需的属性：结论必须能追到某条规则与文档中的某个位置；裁决权必须与「这条要求有多确定可判」相匹配；知识必须能从使用中生长；而这种生长必须处在人的控制之下。我们把这个问题称为**评审知识摄取问题（review-knowledge ingestion problem）**，并以某大型公共服务平台的技术方案预审为场景加以研究。

本文提出 **HARK（Human-Gated Authority-Typed Review Knowledge）**，用四个机制而非一个机制来分别满足上述四条属性。知识成为一个带版本的可验证性分型规则包：**hard** 规则由确定性校验器拥有，产出带位置的证据——包括「缺失」这类 LLM 永远无权主张的证据；**hybrid** 规则由校验器定位候选片段，模型只允许在片段内判断，并由工具侧的证据门禁强制；**soft** 规则只把条目提交给人判断。一个确定性策略从「已确认」集合推出建议结论，最终结论只由专家写入。专家的每个决定成为一层可审计的学习层，可以调参数与措辞，但永远不能提升规则的层级。

系统实现为一个开源 agent harness 的插件（28 条规则，无独立后端）。在 100 份合成方案、253 个人工植入缺陷上，该设计 F1 = 0.798，关键词基线 F1 = 0.222，无误报，结论一致率 85%（κ = 0.76）；未命中项中 80% 以「待人工」条目而非静默通过的形式交给专家。28 条规则中只有 10 条被证明可确定性判定，而四条阻断级规则恰恰最不可判定。

**关键词**：大语言模型；自动文档评审；人在环；神经符号验证；证据锚定；可验证性分型；专家反馈；知识演化

## 1 引言

在大型在线服务平台上线一项变更之前，它的**技术方案**——一份描述背景、架构、接口、数据流、实施计划与风险的模板化文档——必须由一小群资深专家评审。评审是清单驱动的，文档高度模板化，后果是真实的（专家签字），知识既专业又在变化。这些性质让方案预审成为 LLM 辅助的自然目标；也正是这些性质，让「通常做法」变得脆弱。

我们的起点是一次失败的尝试。2025 年做的单体原型把 24 条专家规则各编码成几个关键词，其余全部通过长提示词交给 LLM。结果是：文档任何地方出现「压测」就算压测已被规划；否定句（「暂不安排压力测试」）、占位符（「/」「N/A」）与空章节完全不可见；结论就是模型写进某个字段的那句话，所以阻断级问题不影响结论；什么都没有持久化，第一百次评审与第一次一样无知。把该设计忠实重实现后，在同一语料上评测：只捞回 18.6% 的植入缺陷，每 1 个真问题伴随 2.6 个假问题，与期望结论的一致率不高于随机（κ = −0.04）。这不是模型的失败，是**评审知识进入系统的方式**的失败。

以一条规则为例：「上线前必须做压测」。为该平台撰写的真实方案里，满足它的句子是：「上线前由测试组完成压测并出具报告。」另外三种同样常见的写法：否定式「暂不安排压力测试，视上线后流量再定」；空壳式「压测方案：待定」「压测：/」；以及换词式——要求的内容都在、但关键词族不在——「上线前在准生产环境开展容量演练，500 TPS 下平均响应时间不超过 200 ms」。四句话都含有关键词逻辑所依赖的那个词，只有一句是通过。它们的差别不在措辞，而在于占据了文档的哪个部分、读者会拿它做什么。

实践中主导的三条摄取路线，各自丢掉一个不同属性。**关键词化**把规则变成子串，丢掉语义：出现不等于满足，缺失不等于违规。**提示词化**把规则变成指令，丢掉可审计性：模型看过规则，但它的判断追不回规则，也追不回文档位置。**碎片化**（在历史评审上做检索）丢掉积累：知识每次查询都重新拼装，从不固化。三者都把知识当成「展示给模型的输入」，而不是「系统拥有的资产」，也都默认了同一个假设：一条要求可以交给单一机制。

这个假设下面有两股张力。**可验证性张力**：要求分布在一个谱上，从「实施计划章节存在且非占位」——程序可以精确判定——到「风险分析是否充分」——几乎全靠判断。越不可验证的要求越需要模型；越可验证的，越不该把权力交给模型，因为模型在确定性问题上会犯无法解释的错，而且定位不到错在哪。因此「每条规则交给同一机制」对大部分规则必然错，而且错得并不随机：它恰好集中在组织最在意的那些规则上。**生长张力**：知识必须从使用中生长（每次驳回都是信息），但在人签字的地方，生长不能是单方面的；而权重或过滤阈值的生长，对负有责任的人是不可见的。

本文提出 HARK，把这一表示实现为开源 agent harness 的插件，并在 100 份合成方案与 5 次内部方案端到端评审上评估。四点贡献：

1. **问题与需求**：形式化「评审知识摄取问题」，导出四条设计需求——可审计、权限随可验证性、可生长、有界生长——并为每条给出强制机制与度量工具（表 2）。
2. **可验证性分型规则模型**：类型决定谁可以提出结论——hard 由确定性校验器拥有；hybrid 只允许模型在校验器定位的片段内判断；soft 只为企业排队。缺失是校验器专有的证据类型；候选存在永不算通过；确定性策略只从「已确认」集合推出建议结论（§3.2，图 2）。
3. **评审即反馈**：专家日常的评审动作（采纳／驳回／改写／新增）是学习层唯一的变化来源；系统可以调它，但永远不能提升它；每次评审都盖上生效知识版本（§3.6）。
4. **插件原生实现**：无独立后端、数据库或前端构建；在公开的合成语料上与关键词原型的忠实重实现对比，给出分层、分严重度、分缺陷类型与阈值敏感性分析、证据门禁审计与端到端走查（§4）。

每条属性对应一个问题：RQ1 每个结论能否追到规则与文档位置？RQ2 分型权限是否优于不分型，且类型能否预测剩余判断落在哪里？RQ3 知识是否可测地生长？RQ4 生长是否可归属到人、且可逆？§4 用公开语料回答 RQ1、RQ2，说明 RQ3、RQ4 需要什么，并明确指出本文尚未度量的属性。

图 1 概括了架构。方案以 Markdown 进入（Word/PDF 由上游转换）；解析器产出带源偏移的结构化文档；校验器拥有一切可确定性判定的东西，并为不能的准备好候选片段；模型只看这些片段，且只能「提议」结论；证据门禁只在引文能定位到校验器所选片段内时才接收；策略把已确认结论变成建议结论；而知识唯一的回流路径是专家的决定，写入可审计的学习层。

> 【图 1】架构与权限方向。实线箭头是方案在评审中的流动；虚线箭头是知识变化的唯一路径。hard 检查在校验器层内定案，永不到达模型；模型只能在指定片段内提议，引文不落在那里就被门禁拒绝。学习层可以调参、调措辞、调严重度与状态，可以起草新的 soft 规则，但**不能提升**规则层级——因此没有一条虚线增加系统可单独裁决的内容。

## 2 相关工作

**检查与需求质量。** 自 Fagan 以来，基于清单的阅读一直是文档与代码检查的骨干，综述强调决定产出的是阅读技术而非审查者的天赋。可验证性是需求的一项既定质量属性，而需求「坏味道」（弱词、占位符、缺单位）之所以用轻量确定性分析器来检测，正因为这类检查便宜、可解释、稳定。近期工作保留确定性内核并加上建议能力：Veizaga 等在自然语言需求上检测坏味道并给出消除建议（基于预训练语言模型）；AirReq 把坏味道检测与消除用到商用航空系统需求上，那里一处歧义的代价以适航认证计。我们的校验器继承这一传统，同样把表层线索（否定、占位、缺单位）当作一等证据。差别在范围与权限：坏味道分析器处理单句需求，把整篇文档的判断留给读者；我们的规则面向整份方案，且由类型决定哪些可以自动定案。

**LLM 用于需求与设计评审。** 系统综述梳理了 NLP 与 LLM 在需求工程中的用法；幻觉综述提供了我们据以设计的失败分类；一篇双视角综述把 LLM 同时当作软件验证的工具与必须被验证的产物。多智能体验证器（如 MARV）检索认证标准来检查需求规格；ReqPlan-Eval 依据证据信号把需求路由到人工复核，把裁决权留在评审人手里，并说明其证据不能确立什么。在需求工程之外，同一问题以「评审自动化」的形式被研究：Pornprasit 与 Tantithamthavorn 比较了微调与提示工程在 LLM 代码评审上的效果，发现在同等或更低成本下参数高效微调优于提示；工业评审器则被在线评估其产出的评语质量与有用性。两个背景结果框定了我们的设计：模型判断者不可跨架构互换——同一标注任务在不同模型族上给出系统性的极性差异——所以我们不让模型的置信度替代规则的权限；而 LLM 评测本身仍是开放的方法论问题，所以我们把「机制正确性」与「模型能力」分开度量，而不是报告一个总分。

**神经符号合规评审。** PolicyGuard 把组织政策编译成带类型的关系逻辑规则，规则的基原子由 LLM 从检索到的证据中回答，再由符号求值器套用规则。它满足可审计性、也部分区分了权限，但这种分离是**对称**的——每个原子都由 LLM 回答——而且它没有「这条要求根本不该问模型」的概念，没有反馈回路，也没有有界演化。同样的对称模式出现在用符号约束捕捉溯因错误的场景：Galitsky 与 Rybalov 在过程控制中用物理与传感器约束校验 LLM 的诊断，把符号层当**拒绝过滤器**而不是单条检查的**所有者**。神经符号整合总体上是要让符号成分约束学习成分；我们的贡献是一个具体且静态的约束——证据必须落在校验器定位的片段内，违反该模式的规则包在加载时即被拒绝——外加一个类型，它在读任何文档之前就说明「模型不会参与判断的地方在哪里」。

**人在环控制。** 人在环文献区分主动学习（系统掌控问什么）、交互式机器学习（控制共享）与机器教学（领域专家决定学什么、何时学）。评审一份方案就是机器教学，无论是否这样称呼：专家知道规则、文档与后果。这样的协议需要的不是新的交互隐喻，而是**权限的会计**——哪些决定系统可以单独做、哪些可以准备、哪些必须交出。我们的设计按规则、按类型把这份会计固定下来，写进规则包而不是提示词。

**工业评审反馈与模型判断的边界。** 工业代码评审从开发者反应中学习：BitsAI-CR 先跑规则检查器，再用学习到的过滤器压制规则产生的误报；RovoDev 报告了 Atlassian 内部部署评审器的在线评估；而对真实场景中 agentic 评审器所收反馈的挖掘显示，其大量评语被驳回（多为误报或错位），且驳回是可预测的。这些工作中，学习发生在模型、过滤器或厂商运营的裁剪步骤里；评审人看不到、也回滚不了，而且对象是代码而非设计文档。第二个限制关于输入本身：被评审的文档是不可信内容，能写进文档的攻击者可以直接对判断者说话——针对「LLM 即评审者」的优化式提示注入，在拿不到判断者权重的条件下也能成功。任何「模型是文档唯一读者」的架构都继承了这个攻击面，这也是让校验器（而不是模型）决定模型能读什么的又一理由。

**锚定、引用证据与记忆。** 归因生成把引文附到论断上；而对逐字引用的 claim 级评估表明，「产出一段引文」与「佐证一个论断」不是同一件事。我们加了两条引用文献不需要的约束：引文必须落在校验器选定的片段内；缺失永远不能由模型主张。同样的推理适用于系统记住什么。Agent 记忆是富有成果的方向，但从交互中抽取的记忆可能泄露、也可能被反演出它所概括的内容；由于我们的学习层只存计数、枚举型覆盖、短引文与范例句，而不存自由文本回忆，其暴露面有界、每条可单独审计。自我精炼与反思让 agent 改进自己的输出或记忆，开放式自我修改的 agent 也已出现；我们把「知识的哪一层系统可以自行改变」当作由类型固定的设计决定。我们的协议是严格意义上的机器教学，看板按规则公开已学到什么。

## 3 材料与方法

### 3.1 问题形式化与设计需求

设 K 为一份评审知识（规则、措辞范例、历史决定），S 为基于 LLM 的系统，输入文档 d，输出结论与建议判定。「评审知识摄取问题」即：选择 K 的表示、并为其分配裁决权，使得：

1. **可审计**：每个结论都追溯到 K 的某个元素与 d 中的某个位置，或追溯到校验器产出的「某应有内容缺失」的显式陈述。
2. **权限随可验证性**：S 能否自动提出结论、在检查约束下提出、或只能提示人，取决于该知识元素对 d 的可确定性判定程度。
3. **可生长**：K 从专家与系统的交互中增量更新，不需要独立标注流程。
4. **有界生长**：每次更新都可归属到人的决定、受 (2) 约束、且可逆。

我们以这四条而非「问题级准确率」为主视角，因为对直接提示基线的准确率会被下一代模型追平，而 (1)–(4) 是组织的属性，不是模型的属性。(1)–(4) 也不是悬空的愿望：每条都由具体机制实现，每条都有部署或离线研究可提供的度量工具（表 2）。点明工具对诚实阅读结果很重要，因为涉及「使用中的知识」的两条，恰恰是本文尚未度量的两条。

> 【表 2】设计需求 / 实现中强制它的机制 / 度量它的工具。最后一列写明本文报告什么、刻意留白什么。

### 3.2 可验证性分型规则

规则包是一个加载时校验的 YAML 文件。每条规则含：标识符、评审维度（容量、安全、接口、渠道、数据同步、配置、监控、文档）、严重度（blocker/major/minor）、层级、向 LLM 与专家提出的问题、理由、默认整改建议、可选适用性前置条件、校验器规格、状态。包还带一份**词表**（标题别名、占位符记号、否定记号、关键词族，如「压测」= 负载/压力/性能测试），规则按键引用。规则从不内嵌词汇：语言只活在词表里，所以一个规则包可以被翻译或扩展而不改校验器代码。

层级就是知识的**类型**（表 3）。判据是操作性的：确定性过程能否为这条要求产出带位置的证据（包括「缺失」证据）？如果每个方面都能，就是 hard；如果过程能定位「该要求会在哪里被处理」并标出表层线索（否定、占位、无据断言），但判断仍需要阅读，就是 hybrid；如果没有任何过程能可靠定位相关文本，就是 soft。三种类型的区别不在置信度，而在**谁被允许说话**——这是类型的关键：它是权限，不是概率。

层级决定谁可以说话，不决定什么值得读。因此每条规则还带一个**输出通道**。opinion 通道的结论成为正式意见的编号条款，逐条裁决；checklist 通道的结论（章节完整性、附件编号、表列、时序图消息数）成为单独的「补正事项」附件，评审人一次采纳或豁免。两个通道由同一批校验器产出、同样计入结论策略（§3.5）；拆分把「卡住方案的东西」与「只是需要整理的东西」分开，免得评审人被迫去裁决一打确定成立、又极少决定成败的事实。

> 【表 3】层级语义。注意「谁可以提出结论」是由**工具**强制、而非提示词强制的：模型若尝试越权，会被代码拒绝。

> 【图 2】类型即权限。沿一列往下读，得到该层级允许什么、接受何种证据、对结论贡献什么、学习层可以改什么。类型本身不可被学习层改变；把规则从 soft 提升为 hybrid/hard，需要有人审过的校验器。

两个推论。其一，**缺失由校验器专有**：「未提及压测」无法被引用，LLM 对它的主张在构造上不可验证；只有 hard 校验器产出缺失证据，hybrid 规则找不到候选即转 pending，而 LLM 提交缺失、或以「未提及」「缺失」开头的引文，一律拒绝。这不是文风偏好：缺失是我们语料里最常见的缺陷类别（253 个植入缺陷中 98 个），而这恰恰是生成模型会流利且错误地编造的那类主张；接受它就等于把最高频的真结论换成了最高频的假结论。其二，**候选存在不等于满足**：hybrid 的 statement 检查永不给 pass；若 LLM 什么都没登记，清单显示「已检查、无问题」，而不是「通过」。

类型在加载时静态校验，违反任一不变式则整包拒绝：soft 却带校验器；hard/hybrid 却没有校验器；hard 的校验树里含非决定性检查或 pending 的 no-candidate 分支；hybrid 的 statement 检查是决定性的、或其 no-candidate 行为是 fail；词表键缺失；标识符重复。这些不变式是需求 (2) 的可执行形式：一条「声明的可验证性」与「实际权限」不一致的规则，无法被发布。它们也经得起编辑——因为校验在加载时做，被改类型却没有配套校验器的规则，会在下一次评审时报错，而不是悄悄获得权限。

表 4 给出把遗留清单分型后的包构成，这个分布正是本文诊断的经验核心：28 条里只有 10 条可确定性判定；13 条需要定位到的段落 + 阅读；5 条根本无法定位。更重要的是，**四条阻断级规则全部是 hybrid**（限流与并发控制、加密与签名、闭合的授权链、数据暴露面评估），而 10 条 hard 全是 major/minor。在这个领域，**严重度与可验证性呈反比**——这与「把一切规则当关键词检查」的清单所暗示的正好相反：最有后果的要求，恰恰是程序能定位、但不能定案的。另有 7 条带适用性前置条件，把「不适用」变成显式清单状态而非静默通过；词表含 25 个关键词族、11 组标题、12 个占位符记号、11 个否定记号。

### 3.3 校验器

文档为 Markdown；Word/PDF 由宿主既有的 office 插件在上游转换，所以评审插件不含任何转换器，证据永远是解析器见过的文本。解析器构建：标题树（含 Markdown 标题与加粗行内标题的章节路径）、带单元格范围的表格、Mermaid 时序图（参与者与消息）、以及带偏移映射的规范化文本层（NFKC 折叠、全角转半角标点、去强调、空白折叠），因此任何匹配都报为**源文件范围**而非规范化副本里的字符位置。本领域方案是中文夹英文标识符，故句子在中英文终止符与表格单元格边界处切分，单元格本身也是候选单位；缺失证据带有零长度范围（应在何处出现）与「本应包含它的章节」。

六个校验器族 + 两个组合器覆盖整个包（表 5）。各族的差别在于**能产出什么证据**，而类型正是对着这个差别校准的：section 能说「这个标题缺了」（缺失记录）；table 能指向单元格；statement 能指向句子并标出可疑原因；quantity 能指向数字与单位；mermaid-sequence 能指出缺失的参与者与消息；cross-ref 能指向解析不了的引用。只有当一条要求的每个方面都被「不阅读即可定案」的族覆盖时，规则才是 hard；族能定位但不能定案时，就是 hybrid。

> 【表 5】校验器族。「Uses」计入校验树中的出现次数（一条规则可嵌套多个）；「Dec.」标记 hard 规则可单独依赖的族。

族内有三个设计选择值得说明，各自针对原型中观察到的失败。**否定**在关键词族周围的窗口内检测，而不只看单句，因此「方案不包含压测」与「压测：未规划」都能抓到。**占位符**检测兼顾词汇与结构：词表里的占位记号，也包括正文内容只有标点、只有图片、或只有「待定」这类短语的段落。**图**：两条时序图规则要求 Mermaid，内嵌图片判为 fail 而非替代——图片无法检查参与者与消息，接受它就等于未经审计的通过。三个选择都把工作从模型移到校验器，代价是「语法正确但措辞冷僻」的散文上召回下降——这一权衡在 §4.3 量化。

### 3.4 证据门禁

LLM 只能通过一个工具写结论，该工具的实现即门禁（算法 1）。只有当每一步都通过时才 confirm，否则连同完整原因列表存为 pending，让 agent 修补一次引文，也便于事后分析原因。门禁判定是确定性的、按评审记录，这正是「证据有效率」成为可度量量的原因。

> 【算法 1】证据门禁（简化）。拒绝会被记录而不是抛错：被拒的结论变成专家仍能看到的 pending 条目。步骤：解析规则→soft 直接拒→hard 直接拒→证据为空拒→逐条证据：absence 或引文以缺失标记开头则拒；规范化后长度 <8 或 >300 拒；定位（优先所述章节，再候选片段，再全文首现）；未找到拒；hybrid 且位置不在候选片段内拒。

门禁有两点值得强调，也正是它区别于「请在提示词里引用原文」之处。第一，**位置性**：它检查引文是否落在校验器为该规则选定的片段内，而不只是「文档里存在」。没有这一步，模型可以用一句真实但无关的话满足可追溯性——这正是引用生成模型被报告的失败模式：多数论断都有引文，但真正被引文佐证的少得多。第二，**权限感知**：它在看证据之前就拒绝 hard 与 soft 规则上的结论，所以忽略类型的模型无法靠「引得好」获得权限。代价在算法里可见：被拒的结论是降级而非删除，专家仍能看到，门禁自身的错误率也可审计。

### 3.5 确定性结论策略

建议结论是「已确认结论」的函数，绝不是模型写的东西的函数：

```
confirmed = { i : stat(i) ∈ {confirm, accept, rewrite} ∧ tier(i) ∈ {hard, hybrid, expert} }
m         = |{ i ∈ confirmed : sev(i) = minor }|
verdict   = Fail    若 ∃i ∈ confirmed: sev(i) = blocker
          = Revise  若 ∃i: sev(i) = major 或 m ≥ θ
          = Pass    否则
```

soft 与 pending 只列出、永不计数；checklist 通道的结论与其他已确认结论一样计数，但渲染在编号条款之外，作为补正事项。评审前只有「校验器 + 门禁已确认」的结论参与；评审后驳回的退出、采纳与改写的保留、专家新增的（tier = expert）计入。策略在每次决定后重算，并在专家要写最终结论时作为「建议」显示。最终结论由一个需要具名评审人的工具动作写入，没有其他代码路径能写它；建议与最终结论之差被存为「橡皮图章」的度量。

策略只有一个自由参数：minor 阈值 θ（出厂 3）。它被**暴露**而不是被学习，敏感性见 §4.5；另一种做法——让模型判断「几个 minor 才够」——等于把结论交还给它可靠性本应被约束的那个组件。blocker/major/minor 的不对称不是建模便利，而是编码了组织的规则：任何 blocker 一票否决；又因为四条 blocker 全是 hybrid，这条规则只能等专家确认 blocker 后才触发。所以策略不会在未确认的 blocker 上冒进，§4 也显示它在实践中并不冒进。

### 3.6 评审即反馈：有界演化

评审发生在与 harness 某个 preset 的一次对话里——人设、skill 文档与工具白名单——规定三个阶段。**预审**：专家粘贴 Markdown、给路径或附 Word；agent 解析（按内容哈希恢复被复审的方案）、跑检查，对每个 hybrid 候选先召回该规则的采纳统计、近期驳回理由与措辞范例，然后只对候选片段判断并以逐字引文登记。门禁决定。状态视图渲染建议结论与计数、按严重度排序的结论（含引文与章节）、需裁决项，以及一行清单摘要。

**复核**：agent 通过结构化提问工具分批（每批最多 5 条）呈现结论，每条带引文、建议整改与三个选项：按建议改／不用改／要改但我换个说法。自由文本由**工具**而非模型规范化：「同意」→采纳；「不是问题」「已覆盖」→驳回并把余下文字存为理由；「改成：」→改写；「降为 minor」→采纳并给出仅对该条的严重度覆盖（不动规则）；「你漏了」→新增，尽量匹配最接近的规则。「其余全部采纳」只采纳已确认项，pending 必须逐条看。**定稿**：渲染正式意见、作为文件交付，并原子更新知识层；之后的决定会重开记录并要求新版本。这个协议是**用日常工作完成的机器教学**：专家从不额外标注，而他本来就必须做的每个决定，都变成一个带类型的事件。

知识存在于两层。**出厂层**是规则包；**学习层**是一组记录，读取时合并覆盖（表 6）。每次写入追加一条审计记录，每次评审盖上生效知识版本 `pack@ver+ovN`，其中 N 为有覆盖生效的规则数，因此一次评审可以对着产生它的那份知识复现。

> 【表 6】学习层：同一存储域里的七张表，各自的写入路径与读取用途。没有一张表由模型单独写入——agent 提议，评审关闭或专家的显式动作提交。

边界被刻意做成不对称的。系统可以在白名单内改参数、改措辞、改严重度与状态，也可以起草新的 **soft** 规则，但**永远不能提升规则层级**：自称 hybrid/hard 的草案必须带有人审过的校验器。权限的提升因此在构造上就是人的行为，这是我们对需求 (4) 的读法。可逆性是对称的：把字段设回出厂值即删除覆盖，所以「改回去」与「从未改过」在生效版本里不可区分；重置在一步内移除某规则的全部覆盖（并留审计），但保留其统计。

### 3.7 实现

我们把它实现为 **HARK**，一个开源对话式 agent harness 的插件包；harness 已提供对话循环、模型访问、文件访问、结构化提问工具、交付工具、人设/skill 机制、JSON 存储服务、带访问控制与布局槽位的 web 服务器。插件新增：一个纯函数引擎（解析、校验、门禁、策略、记忆聚合、意见渲染；无 I/O、无时钟）、含表 6 七张表的存储域、只在评审 preset 内可见的九个工具（表 7）、三条不经模型的斜杠命令、宿主访问控制下的 HTTP API，以及带总览／规则页／侧边助手的看板。没有独立后端、数据库、向量索引或前端构建；客户端是单个 84 kB 的 bundle。

> 【表 7】评审 preset 的工具面。权限由工具而非提示词强制；最后一列列出工具以**类型化错误**拒绝、而不是静默成功的条件。

工具契约用 schema 校验，共 13 个类型化错误码；决定之后再跑检查会被拒绝（会产生孤儿反馈）；已评审的方案按「恢复」而非「重复」处理。引擎的纯粹性正是 §4 离线评测得以成立的原因：回答线上评审的同一批函数，被评测脚本在语料上调用，模型换成确定性判断者，因此度量的是机制、且没有模型方差。参考机上 100 份方案 × 23 条可验证规则约 1.6 s，远低于每「规则—文档」对 1 ms，相对单次 hybrid 判断的模型延迟可忽略；评审成本由「送进模型的候选片段数」主导，而非确定性层。

插件按常规作为 profile 插件安装；规则包是数据，所以第二个领域 = 第二个 YAML + 一份词表，规则改动下次评审即生效、无需重启。看板由宿主自己的 web 服务器在宿主的访问控制下提供，因此不引入新的认证面；左面板给出评审总览（日历、趋势、可就地裁决的方案列表）、规则状态（出厂／已学／候选）与评测运行，右侧栏 tab 让进行中的评审与对话并排。

## 4 结果

### 4.1 设置

**语料。** 公开的生成器（种子 20261029）产出 100 份方案、253 个人工植入缺陷，覆盖 23 条可验证规则——98 个「缺失」、37 个「否定」、52 个「占位」、66 个「关键词在场但内容为空」——取自若干短语池，每条规则至少有 3 种满足写法与 4 种不满足写法，其中至少一种刻意避开词表关键词。期望结论为 30 通过、47 建议整改、23 不通过，其中 30 份按 30 条历史专家意见 15/14/1 的分布成形。语料是合成的，因为原始方案不能公开；它度量机制正确性与基线相对差距，不度量业务语义判断。公开的自检对每份方案重算：每条被满足的规则应通过其校验器、每条被植入的规则应失败，因此报告的误报可归因于机制而非语料。

**语料反过来测了出厂规则包。** 自检还抓到一个缺陷，且不在基线里而在出厂包里：第一轮生成在每份列了原型附件的方案上失败——DOC-002 的附件清单正则捕获的是附件编号**后面的词**而不是编号本身，于是交叉引用解析器拿「prototype」去比「1」，把明明列出的附件报成「清单中缺失」。正则改为捕获编号后修复，该用例现已成为公开自检的一部分。这样形状的缺陷在单次评审里不可见，在一百份里则无处躲藏——这正是把语料与规则一起发布的实际理由。

**配置与指标。** 我们比较 B0（复刻 2025 原型：每规则 3–5 个子串、无否定识别、无结构、无证据，但采用同一结论策略，比原型更宽松）、分型设计 S-full（校验器 + 候选 + 门禁 + 策略 + 记忆），以及 S−verifier（hybrid 语句在全文上判断）。插件不带模型客户端；hybrid 判断走可插拔 judge。本文报告确定性 flag judge：当校验器标记某个候选片段为否定、仅断言或占位时，它就在该片段上提出结论。它度量机制而非 LLM 能力；LLM-judge 配置（直接提示、关掉门禁、模型自定结论）留给姊妹报告，不做近似。对齐粒度为（评审，规则），并区分两个常被混为一谈的量：**包内一致**——预测的规则命中植入缺陷或已满足的要求；**包外新增**——专家提出的、规则集中不存在的问题。只有前者可与基线比较；后者单独作为**候选规则**报告（§3.6），永不并入 precision 或 κ。指标为：precision、recall、F1（按方案 bootstrap 区间）、严重度加权召回（权重 3/2/1）、结论准确率、macro-F1、Cohen's κ（不加权与二次加权）、证据有效率（通过门禁的模型登记占比）、待人工覆盖率（以开放条目示人的未命中占比）。每个配置重复三次得到逐字节相同的指标，故区间是按方案的 bootstrap 区间，而非重复方差。

### 4.2 分型 vs 关键词化（RQ2）

B0 产出 47 个真、124 个假、206 个漏；S-full 产出 168 个真、0 个假、85 个漏，ΔF1 = +0.564（按方案 F1 的配对 Wilcoxon，p < 0.001；结论正确性 McNemar b/c = 64/7，p < 0.001；均通过 Holm 校正）。S-full 在 42/100 份方案上 F1 = 1.0，逐方案 F1 中位数 0.857。

B0 的错误形态正是分型所预言的，而且是可量化的。在关键词无信息量的 13 条规则上（否定、占位、空壳写法占主导），B0 的 precision 恰好为 0.00；它的 124 个误报全部来自六条规则，其中三条所依赖的词汇在合格文本里同样常见（加密、渠道标识、限流）。召回也好不到哪里：23 条规则里 15 条低于 0.15，包括时序图规则（0.13）与压测规则（0.29），因为满足的写法常常绕开词表——那次「容量演练」通篇没提「压测」。它的结论一致率不高于随机（κ = −0.04；30 份「通过」里 17 份被判「不通过」），复现了 2025 年那次失败：一份「声明过但不可验证」的清单驱动了结论。

表 9 把同一批结论按层级与严重度拆开。**层级结果是本文的机制主张**：hard 规则以 precision 1.000、recall 0.880 定案，hybrid 规则以 precision 1.000、recall 0.387 定案；在 B0 下对应 precision 为 0.698 与 0.085。分型因此不只是改善聚合指标：它移除了产生假结论的那个失效模式，剩下的是集中在「真正需要判断处」的召回代价。

> 【表 9】按层级与按严重度的结果（S-full vs B0）。召回差异度量各权限路径能定案什么；严重度行显示最有后果的规则召回最低，因为四条 blocker 全是 hybrid。

严重度那几行对组织是个警告：最好召回不在 blocker 上而在 major 上（0.702 vs 0.486），因为四条 blocker 恰恰是「无法从表面读出是否满足」的规则——闭合的授权链、健全的加密方案、足够的限流策略，都需要一个读者。于是，把清单当关键词检查来部署，最容易失败的正是「卡住上线」的那些结论——这就是可验证性张力的经验形态。

### 4.3 剩余未命中在哪里（RQ1）

85 个未命中，全部要么是**计划内的待人工状态**，要么是**决定性校验器已知的取舍**；没有一个是「定位到了缺陷却静默通过」。其中 68 个是转为 pending 的 hybrid 缺陷——27 个缺失、30 个空壳（flag judge 无法定案），加上 11 条被门禁拒绝的否定/占位片段——因此**全部未命中的 80% 以开放条目示人**而非被隐藏；一次评审浮现 6–13 条 pending，中位 9。剩下 17 个是「以关键词在场为决定性判据」的 hard 规则（压测语句 7、渠道标识 5、变更清单表 5），它们漏掉占位与空壳写法——这是让这些规则全自动的已知代价。

表 10 与图 4 按缺陷类型拆开机制的覆盖，与关键词基线的对照是「分型买到了什么」最清楚的一句话：关键词基线只在关键词完全缺席时才发现缺失（45/98），其余三类几乎一无所得（否定 1/37、占位 0/52、空壳 1/66）——它在「缺失」上的表面能力也正是它误报的来源，因为它分不清「关键词缺席是因为要求没满足」与「关键词缺席是因为作者换了说法」。分型设计把四类都抬起来，剩下的次序——缺失 0.72、否定 0.84、占位 0.81、空壳 0.36——就是「仅靠结构能定案什么」的次序。

### 4.4 证据门禁

确定性 judge 提交了 53 条 hybrid 结论：42 条通过，11 条（20.8%，分布在 10 份方案）因过短被拒——否定与占位句常常短于 8 字符引文下限。被拒的结论**降级为 pending 而非丢弃**（它们正是 judge 无法引用的否定与占位片段），因此门禁的代价是 11 条已定位的真结论（recall −0.043）、零个假结论，且每条仍对专家可见。没有发生缺失、未找到或越出候选的拒绝——这对「引用校验器自己片段」的 judge 是预料之中的。证据有效率因此为 79.2%：五次登记中有一次首次即失败，而失败永远是**所供证据的属性**，从不是结论背后的真假。

这个数字应当读作门禁在真实模型上有效性的**上界**而不是下界。确定性 judge 已经在引用校验器给的片段，却仍会触到长度下限；一个凭记忆引用的生成模型还会触到定位检查，而门禁的用途正是让这种失败可见、可修，而不是静默。结果还指认了「引文下限」——为阻止一两个词的「证据」而设——在整句占位片段上是一个需要重新审视的参数。

### 4.5 片段作用域与结论策略

在确定性 judge 下 S−verifier 与 S-full 完全相同（ΔF1 = 0，b/c = 0/0）：扩大搜索范围增加了候选片段，但没有一个携带线索，而 judge 从不在给定范围之外引用——所以「片段作用域」的贡献是 LLM judge 的属性，应在那里度量。S-full 的建议结论与植入结论在 85/100 份方案上一致（κ = 0.76；通过/整改/不通过混淆矩阵 [[30,0,0],[6,41,0],[4,5,14]]）。全部 15 个不一致都是**少判**，由 pending 的 hybrid 结论造成——9 份「不通过」的 blocker 缺陷是 hybrid，6 份「整改」的 major 缺陷是 hybrid——且没有多判，与「只计已确认结论」的策略一致。

唯一的自由参数表现符合「策略参数应有的样子」（表 11）：θ = 1 时单个 minor 就足以要求整改，在 15 份「通过」上多判；从 θ = 3 起建议不再变化，因为本语料里带三条及以上 minor 的方案同时带 major。我们保留 θ = 3，并把这段平台区当作「结论对合理区间内的精确取值不敏感」的证据——这是模型写出的结论不会有的性质。

### 4.7 协议在内部方案上跑通

语料之外，我们让系统跑了三份为平台撰写的技术方案：一份改版后复审一次，一份为验证「恢复」重跑一次，共五次运行。运行者是构建该系统的团队，因此它们记录的是机制，而不是独立的专家研究。五次运行共提出 58 条结论：40 条由校验器定位、12 条由模型在候选片段内判断、6 条由操作员新增。门禁拒绝了 12 条模型判断中的 3 条，理由完全相同——引文落在校验器定位的片段之外——因此 §3.4 的拒绝路径在真实散文上（而不只在植入缺陷上）被走通了。hard 与分型规则把每份方案都判为不通过；进入最终结论的两次评审维持该结论，操作员对 18 条需裁决结论采纳 15 条、驳回 3 条、无一改写。学习层确实被写入：五次运行后它为 13 条规则保存了统计、21 条范例，且没有任何规则改变层级。

## 5 讨论

### 5.1 对研究问题的回答

**RQ1：可验证性张力。** 在本语料里它不是假设而是可度量的，而且有方向：**决定能否上线的规则，恰是最不能靠结构判定的规则**。四条 blocker 全是 hybrid；blocker 上的召回（0.486）低于 major（0.702）与 minor（0.675）。因此，一份被调成「全自动」的清单，恰恰会在「宽松代价最高处」既自动又宽松；而一份被调成「对 blocker 严格」的清单，又会产生一批终究要人来裁决的机器结论。三分型是我们找到的最小机制，它让这股张力显式化而不是被平均掉：先给每条规则指定权限路径，再谈这条路径的成绩。

**RQ2：分型买到了什么。** 分型移除了失效模式，而不只是削弱它。B0 下「规则声明」与「所报结论」的关联两个方向都断了：124 个假结论、206 个漏，结论等同随机。S-full 下没有任何结论缺少定位引文，召回升到 0.664、严重度加权 0.649、结论一致率 κ = 0.76。有意思的不是 F1 的差距，而是它的构成：增益集中在否定（2.7% → 83.8%）与占位写法（0% → 80.8%），也就是「含有关键词、意思却相反」的文本。关键词逻辑在那里按构造必错；仅靠结构就能捞回大部分，剩下的才需要模型。

**RQ3：证据是否改变了行为。** 门禁没有让机制更准；它让机制**可审计**，而审计改变了我们自己的行为。五分之一的登记没过门禁，且失败永远是证据属性的失败：引文太短，而不是定位错了（因为确定性 judge 引用的是给它的片段）。所以我们不主张门禁在本配置下提高了 precision——precision 早已饱和——而主张它产出了一个评审人可据以行动的信号，并让链条上最弱的一环（凭记忆引用的模型）以「被拒绝」而非「不可验证的主张」的形式现形。它是否提高真实模型的 precision，是计划中的 LLM-judge 消融要回答的第一个问题。

**RQ4：专家决定能否就是知识。** 这个机制存的是**决定**而不是**偏好**：每次评审决定都带问题标识、判定、可选改写与时间戳写入，每条规则的聚合召回是对这些行的查询，而不是重新训练的参数。这个设计有我们尚未支付的代价——没有专家评审过这 100 份合成方案，记忆层只被确定性 judge 驱动过——也有可以精确陈述的好处：记忆不会与规则漂移，因为它与规则用同一套标识符做键，而且专家能看到并逐条修正任何一行。「学习发生在哪一层」因此是一个带审计轨迹的设计决定，而不是模型的涌现属性。

### 5.2 为什么权限是不对称的

两个方向的算术不对称。一个假结论的代价是评审人的信任，若进了正式函件则还要与提交团队争论；这类东西攒够了，部署就结束了。一个漏结论的代价，是评审人自己记忆里的一行——前提是他还有读文档的习惯，而 pending 列表正是为此设计的。策略把这个不对称编码进去：系统只能从**已确认**的 blocker 推出「不通过」，但它随时可被推翻，且它从不写最终结论。这也是我们不在策略的任何地方使用模型自定结论的原因：模型自定结论是没有审计轨迹的单点故障，而策略的输入是人可以逐行检查的行。

这个不对称有一个应当说明的边界：它假定评审人**会读** pending 列表。在我们的走查里，漏掉的埋点缺陷是五行中的一行；一个信任四条已确认结论的评审人会以正确的理由签下「不通过」，却始终没看到第五条。承载这个风险的是界面而不是策略；插件把 pending 条目做成一等对象并强制逐条记录确认，但「这是否足够」需要现场研究。

### 5.3 与自动评审器的位置关系

近期工作大多把自动评审当作**文本生成任务**来度量：给一个 diff 或设计，产出开发者愿意接受的评语。那个框架优化「讨人喜欢」，而我们所知最大规模的工业部署报告的正是开发者对**单条评语**的接受率——这个指标适配 diff 与评语流，不适配结论。我们的框架是它的补集：产出物不是评语流，而是带可审计推导的结论；正确性的单位是一条规则，因此系统更像是与**合规清单**比较，而不是与人比较。两个框架在「清单本身用散文写就」的地方相遇：设计文档的神经符号验证同样有「用结构约束模型」的冲动，但它用结构去检查模型的抽取；我们用结构决定**谁被允许说话**。

合规语境还给出一个我们尚未充分使用的约束。安全需求评审与认证审计本就围绕控制目录组织，而可追溯的要求正是那些流程当作证据的产物。如果规则包的标识符能对齐目录，评审就能直接引用控制编号，记忆也能在认证机构关心的粒度上聚合。我们让规则 schema 保持与这种可能对齐（每条带维度与来源字段），但把映射留给未来工作，因为它改变的是评审的本体，而非实现。

这个框架有两个风险值得点名。其一是监管的：如果评审支撑了某项受监管的决定，产出物及其来源可能获得法律分量——这正是欧盟 AI 法案的文件义务成为设计下一步约束的理由。其二是模型本身：读不可信方案的判断者是提示注入的目标，而累积专家改写的记忆是隐私目标。两者都不是门禁能解决的；两者都是「保持模型权限狭窄」的理由，而这就是设计的主防线。

## 6 局限与未来工作

**语料是合成的。** 100 份方案由短语池生成，因此度量的是对植入缺陷的机制正确性，而非对真实设计意图的判断质量。三个后果无法回避：满足的写法在构造上就满足；词汇比现场文本窄；结论标签在构造上正确，而非由专家一致同意得出。我们通过「在条款级别植入缺陷、并从策略本身导出期望结论」（有 blocker 即「不通过」）来缓解第三条，所以准确率度量的是策略的执行而非某种品味。缓解不等于消除差距；下一步自然是带两位独立专家标注的匿名真实方案语料，而脱敏流程已在公开管线中写明。

**判断者是确定性的。** hybrid 召回（0.387）是下界，因为 flag judge 只看结构线索、按设计把语义情形留作 pending；反过来 precision（1.000）是上界，因为同一个 judge 从不编造引文。片段作用域显示「无效果」，恰恰因为 judge 只引用给它的片段，所以「片段本应起的作用」——不让生成模型游走——在此未被检验。计划中的消融覆盖三种 judge 设置（全文直接提示、候选片段提示、关掉门禁的提示），两个开源模型、固定解码参数、同一语料，并把门禁的拒绝分类作为主要结果报告。

**没有独立专家在环。** 贡献的在线形态——评审决定成为记忆、记忆改善后续评审——未被检验。§4.7 的五次内部运行说明回路闭合、学习层被写入，但操作员就是写规则的团队，因此其采纳率不能说明外部专家如何，五次运行也画不出学习曲线。这些运行检验的是管线（决定记录、记忆聚合、范例召回）与离线聚合器，而不是「每条规则的专家召回随接触次数上升」这一主张。该主张需要纵向部署：同一批评审人、同一能力、一段无记忆的基线期与一段有记忆的干预期，以逐规则召回、驳回率与改写率为结果。我们描述测量计划与 schema 而不报告效应，并认为这是本文最大的开放问题。

**规则包的范围。** 覆盖单一能力评审清单的 28 条规则不是一个评审标准。分型机制与规则无关（它接受任何带声明校验器的规则），但构成表（§3.2）显示**层级配比是领域的属性**：文档类规则多为机械，安全类规则多为语义。不同领域需要不同配比，而「如何不靠品味地选层级」是开放的；我们的做法是先写校验器、再定层级，这让选择可追溯，但不自动。

**语言与词表。** 语料、词表与规则是中文，为电力服务场景；机制与语言无关，但线索列表有关。移植是配置任务而非改代码，词表随包做版本，但每次移植都需要自己的自检，因为在一个领域的措辞上校准过的线索列表，在另一个领域会**静默失败**，只有按领域的自检才能抓住。

**结论策略与人因。** 结论策略是确定性的，其阈值在本语料上不敏感，但它假定评审人会读 pending 条目，而我们没有度量这一点；我们也没有度量「当建议结论偏向宽松方向错时，专家是否更频繁地推翻它」——而这正是设计所倚赖的不对称。两者都是研究设计问题而不是实现缺口，都应与纵向部署一起做。

## 7 结论

建立在 LLM 之上的评审系统往往给模型两种角色之一：写评语，或定结论。我们主张第三种安排：模型永不单独定案，程序永不定案它检查不了的东西，专家的决定就是系统累积的知识。它的构造单位是规则，证据单位是引文，权限单位是层级，学习单位是那一行决定。

在 100 份方案、253 个植入缺陷的语料上，这一安排无误报、捞回三分之二的缺陷、在 85% 的方案上与植入结论一致（κ = 0.76），而关键词基线停在随机水平。更有启发的是它在哪里输：**决定能否上线的规则，恰是需要读者才能判定满足的规则**，而剩余未命中集中在「只规划、未实现」的散文上。回路也在语料之外闭合：三份内部方案五次运行、58 条结论、18 个操作员决定，门禁在真实散文上拒绝了三条模型判断。我们把这些读作「设计约束是对的」的证据——模型该读，不该定——以及由此展开的议程：一个值得信任的判断者，一次「决定是否改善后续评审」的纵向检验，以及规则包与合规工作已在使用的控制目录之间的映射。
